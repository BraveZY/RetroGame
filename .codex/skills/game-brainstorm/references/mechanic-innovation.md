# Mechanic Innovation and Prototype Proof

Use this reference when a candidate needs a rule-level rewrite. Innovation means a player repeatedly makes a better or different decision; it does not mean combining unusual themes.

## Micro-Innovation Delta

Before expanding a candidate, name one primary change:

| Changed relationship | Must explain |
|---|---|
| Goal | What players optimize or protect now |
| Consequence / failure | How success and mistakes change future play |
| Information | Who knows what, when, and how that changes action |
| Space / tempo | How position, routes, order, or timing reshape priorities |
| Role / social relation | How ownership, cooperation, rivalry, or spectatorship changes |
| Input mapping | How player action visibly and continuously changes the world |
| Mechanic relationship | How two systems alter one another |

If the candidate cannot name a primary change and its new decision, it is probably a theme variation or feature pile.

## Mechanic Coupling Formula

Use this only when the candidate actually combines two mechanics:

1. **Mechanic A**: The player physically or mentally ___; the outcome is ___.
2. **Mechanic B**: That outcome changes B by ___.
3. **Return effect**: B's new state changes the next use of A because ___.
4. **New decision**: The player now chooses between ___ and ___; that choice would not exist in A or B alone.
5. **Removal test**: If A is removed, ___; if B is removed, ___.
6. **Smallest proof**: Test only this loop with ___.

If step 3 or 4 is weak, the mechanisms are merely adjacent. Keep the stronger one and park the other.

## Rule Rewrite

Complete these sentences before calling a candidate strong:

1. **Reality anchor**: This is for ___ playing ___ with ___ input in ___-minute rounds.
2. **Baseline**: Similar or current play makes players repeatedly ___.
3. **Changed rule**: This candidate changes ___ so that ___.
4. **Primary micro-innovation**: This changes the relationship between ___ and ___, creating ___.
5. **Mechanic coupling, if any**: ___ action/result changes ___ state, which changes the next ___ choice.
6. **Recurring choice**: Every 10-30 seconds, players choose between ___ and ___.
7. **Visible consequence**: A correct or wrong judgment immediately changes ___.
8. **Input value**: The player uses ___; this is meaningful because ___.
9. **Content runway**: The same rule can vary through ___, ___, and ___.
10. **Smallest proof**: Test the rule with ___, without building ___.
11. **Kill condition**: Park or stop it if ___.

If one sentence needs lore, a second unrelated mechanic, or an unverified technology claim to work, simplify or park the candidate.

## Useful Rule Levers

Use a lever only when it improves the recurring choice.

| Lever | Productive question |
|---|---|
| Position and space | What does being in the right place protect, reveal, block, or sacrifice? |
| Timing and tempo | When is waiting safer but worse than acting now? |
| Information | What must players infer, reveal, hide, or communicate? |
| Shared responsibility | What can one player optimize that creates risk or opportunity for another? |
| Recovery | How does a mistake create a playable recovery instead of a flat fail state? |
| Resource / capacity | What limited resource makes the choice non-obvious? |
| Input signal | What coarse, reliable signal can change a world state rather than trigger a command? |
| Content variation | Which encounter variables change while the central decision stays intact? |
| Mechanic coupling | Does the output of one mechanic become the changing state and next constraint of the other? |

## Stress Test

- Can a tester describe the tradeoff after one 90-second round?
- If two mechanics are used, can the tester explain how each one changes the next decision in the other?
- Does the game visibly respond to the central action every few seconds?
- Does the rule work without lore, UI explanation, or progression?
- Can three encounters reuse it without new core mechanics?
- Can the specified input reliably carry the necessary precision, player count, and play space?
- Is the uncertainty small enough to test before full production?

If the answer is no, do not add features. Reduce the loop, change the mapping, or park it.

## Prototype Proof

| Field | Meaning |
|---|---|
| Smallest prototype | Paper for decisions, spreadsheet for systems, graybox for space/timing, text for social rules, fake-input before real recognition. |
| Test group | State the intended player type and a small sample size. |
| Observation | Watch comprehension, strategy talk, voluntary replay, cooperation, fatigue, and recognition failures. |
| Threshold | Define a pass threshold before testing. |
| Kill condition | State the observation that ends expansion. |
| Next evidence | Notes, sketch, keyframes, recording, graybox, or a brief only after the rule is credible. |
