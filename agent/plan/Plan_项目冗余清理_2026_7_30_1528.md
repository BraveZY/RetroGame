# RetroGame 项目冗余与过时内容清理方案

## 1. 目标与范围

在不改变现有游戏功能和目标平台能力的前提下，降低仓库体积、消除误提交的生成物，并使项目可以从版本库可靠重建。UnityMCP 已获授权整体移除，不再是保留条件。

本方案原用于定义清理顺序、责任边界、验证门槛与回退方式；后续已获得 UnityMCP 整体移除的明确授权，实际执行记录以“当前执行状态”和对应 Task 为准。

后续候选、优先级和验收边界见 [Plan_后续冗余清理_2026_7_30.md](Plan_后续冗余清理_2026_7_30.md)。

### 不变量

- UnityMCP 前端与 IndexService 已在用户明确授权后整体删除；其他候选仍不得按文件名直接删除。
- 不按目录名（如 `_Ban`、`Examples`）直接判定可删；资源必须经过引用、构建和人工用途确认。
- 保留当前工作树中的用户改动；执行阶段按目录精确暂存，不使用 `git add .`。
- 每批删除均可由 Git 恢复；二进制/平台插件删除前必须完成对应平台构建验证。

## 3. 分阶段执行方案

### 阶段 A：先建立可重建的 source of truth

**目标**：明确每类内容是源码、可再生输出、随包分发二进制还是仅本地状态。

1. 确认 Unity 版本的唯一来源；将团队需要复现项目所必需的 `ProjectSettings` 文件与 Unity 版本策略写清。
2. 确认 `Packages/packages-lock.json` 的团队策略：若目标是可重复依赖解析，则应纳入版本控制；若刻意不跟踪，则必须有可验证的替代解析记录。
3. UnityMCP 的两条分发链（WebFrontend 与 IndexService）已因整体移除而终止，不再需要补回源码或构建说明。
4. `node_modules`、`bin/Debug` 及其专用 ignore 规则已删除；删除后 Unity 编译验收已通过。

**完成标准**：干净环境中的成员能知道 Unity 版本与依赖解析方式；已移除的 UnityMCP 不再需要构建/分发说明。

### 阶段 B：低风险仓库卫生清理

**目标**：移除既不参与 Unity 运行、也不承担可复现构建职责的编辑器残留。

候选范围：

- `Assets/.vscode/launch.json`
- `Assets/StreamingAssets/web/.vscode/settings.json`

执行要求：

1. 先确认没有开发脚本、README 或团队约定依赖这两个文件。
2. 删除文件后，在 `.gitignore` 中添加精确规则，只忽略这两个 Assets 内 IDE 目录，不扩大到业务 `StreamingAssets/web`。
3. 打开 Unity 项目，确认 Console 无新增导入错误；构建一次当前主目标平台，确认 StreamingAssets 内容不受影响。

**完成标准**：Git diff 仅包含上述文件和精确 ignore 规则；Unity 可正常打开且目标构建成功。

**当前进度**：候选文件已删除，未新增 ignore 规则（仓库现有 `.vscode/*` 已覆盖两处）；静态引用扫描为零。尚未执行 Android 主目标构建，故本阶段保持 **⚠️ 待目标构建验证**。

### 阶段 C：清理失效命名二进制

**目标**：移除 Unity 不会以插件身份加载、没有资产引用的历史改名残留。

候选范围（均已删除）：

- `Assets/Plugins/Android/pose-release.aar.1`
- `Assets/Plugins/Newtonsoft.Json.dll.1`
- `Assets/Plugins/x86_64/onnxruntime.dll.1`
- `Assets/Plugins/x86_64/onnxruntime.dll.locked`
- `Assets/Plugins/x86_64/onnxruntime_providers_shared.dll.1`

已完成静态验收：五项均为 `DefaultImporter`，且 GUID、路径和代码读取扫描无残留。ONNX 三项已通过 Unity 编译回读；本轮两项仍需 Android/Windows 目标构建验证。

执行要求：

1. 对每个候选重新核对 `.meta` importer、GUID 反向引用和代码中的文件路径读取。
2. 将候选分为 Android、Windows、托管 DLL 三组，禁止混为一次无验证删除。
3. 每组删除后进行对应构建：Android 组出 APK；Windows 组出 Windows Standalone；托管 DLL 组完成 Unity 编译和关键启动流程。
4. 若构建或运行出现动态库缺失、程序集加载或模型初始化异常，立即恢复该组，不推进下一组。

**完成标准**：每个已删文件都有“无引用 + 对应目标构建通过”的记录；未验证平台上的候选保持不动。

### 阶段 D：macOS ONNX Runtime 重复（已撤销）

托管 ONNX Runtime 及其 macOS 副本已经随动作分类链整体删除，故“保留一份、删除一份”的原方案已失效。本阶段标记为 **✅ 不再适用**，不触碰仍保留的 `detect_pose`/YOLO/RKNN 原生姿态检测链。

### 阶段 E：示例、归档和 `_Ban` 目录的人工裁决

**目标**：识别可按产品需求删除的非运行内容，但不把静态未引用误判为无用。

优先审查对象：

- 示例：`Assets/Spine Examples`、`Assets/FFmpeg/FFmpegDemo`、`Assets/NatML/Examples`、`Assets/TextMesh Pro/Examples & Extras`、`Assets/Array2DEditor/Example`、`Assets/Nbjson/JsonNetSample`。
- 历史归档：`Assets/FFmpeg/Plugins/IOS.zip`、`Assets/热更打包流程.rar`、`ProjectSettings/ProjectSettings.rar`。
- 名称为 `_Ban` 的资源或代码目录。

执行要求：

1. 对每个根目录检查场景、Prefab、ScriptableObject、Addressables/AssetBundle、`Resources.Load` 和反射/字符串路径。
2. 由项目负责人确认其是否服务于当前产品、内部调试、工具二次导入或历史备份。
3. 示例目录优先采用“先移出 Assets 并完成编译/构建验证”的方式，不与业务资源一起删除。
4. 归档文件先迁移至仓库外的文档/制品存储并校验可取回，再从 `Assets` 删除；不得只因没有 GUID 引用而删除。

**完成标准**：每个清理根目录具备负责人结论、引用审计、目标构建验证和可恢复位置。

## 4. 验收矩阵

| 清理类别 | 必需验证 | 不足以证明安全的验证 |
| --- | --- | --- |
| IDE 残留 | Unity 导入无新增错误 + 主目标构建 | 仅 `git status` 干净 |
| Android 二进制 | APK 构建 + 设备或运行时关键流程 | 仅 GUID 无引用 |
| Windows/macOS native plugin | 对应 Standalone 构建 + 原生能力冒烟 | 仅文件 hash 相同 |
| UnityMCP 生成物 | 在干净环境可从源码重建，或已确认二进制分发 | 仅文件位于 `bin`/`node_modules` |
| 示例与 `_Ban` 资源 | 引用追踪 + 构建 + 产品负责人确认 | 仅目录名称或未出现在 Build Settings |

## 5. 回退与提交策略

- 每个阶段独立提交，提交前只暂存该阶段列出的路径。
- 删除后发生问题时，使用对应阶段的提交回退，不夹带项目设置、依赖升级或业务功能改动。
- 大型归档迁出前保留校验值与可访问位置；未验证前不销毁唯一副本。
- 每阶段结束记录：删除清单、释放体积、构建目标、Console/运行结果、未验证的平台。

## 6. 待确认事项

1. 当前发布目标是否包含 Android、Windows、macOS ARM64、iOS；这决定阶段 C/D 的验证范围。
2. UnityMCP WebFrontend 和 IndexService 是开发工具、运行时依赖，还是已废弃组件。
3. `_Ban` 命名是否代表已停用内容，还是仅历史命名规范。
4. `ProjectSettings` 与 `packages-lock.json` 的现有忽略规则是否是团队有意策略；若不是，应在阶段 A 优先修正。
