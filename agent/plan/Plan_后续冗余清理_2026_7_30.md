## 执行顺序与验收

### 1. 先闭环既有删除的目标构建

**目标**：确认阶段 B/C 的删除未影响真正交付包。

1. 使用当前项目的 Android 构建入口执行“直接打包（Skip）”，不触发 HybridCLR 资源再生成；保存 APK 路径、BuildReport 与 Console 结果。
2. 用对应 Windows Standalone 支持模块完成一次 Windows 构建，验证被删除的 `Newtonsoft.Json.dll.1` 不参与程序集加载。
3. Android APK 检查 `lib/`、`assets/` 和 Gradle 日志，确认没有 `pose-release.aar.1` 或缺失插件错误。

**完成标准**：Android APK 与 Windows Standalone 均构建成功；Console 无本轮新增错误。没有 Windows 支持模块时，此项保持 `⚠️ 待验证`，不可用静态扫描替代。

### 2. 建立项目可重建 source of truth

**目标**：让新成员可解析同一 Unity 版本和同一 UPM 依赖图。

1. ✅ 已从 `.gitignore` 移除 `ProjectSettings/ProjectVersion.txt` 和 `Packages/packages-lock.json` 的忽略规则。
2. ✅ 当前 `ProjectVersion.txt`（`2022.3.62f3`）和已解析的 `packages-lock.json` 已纳入版本控制；`ProjectSettings.asset` 已被跟踪，无需重复操作。
3. ❔ `ProjectSettings/EditorBuildSettings.asset` 当前被忽略且 `m_Scenes: []`；必须由负责人指定发布场景及顺序后再纳入版本控制。不得从 `Assets/Scenes`、示例或 `_Ban` 目录猜测选择。
4. 在干净副本中以该版本打开项目，读取 lockfile 解析结果并完成一次编译和 Android 构建。

**完成标准**：版本文件、manifest、lockfile 与已确认的 Build Settings 均在 Git 中；干净副本不依赖个人缓存即可完成包解析、脚本编译和 Android 构建。

处理步骤：

### 5. Android ABI 与同名 native 库审计（高风险、高收益）

候选包括：

- `Assets/Plugins/Android/arm64-v8a/libtransfrompose.so`
- `Assets/Plugins/Android/arm64-v8a/libtransformpose.so`
- `Assets/Plugins/Android/libs/x86/**`

当前 Android 架构掩码为 `AndroidTargetArchitectures: 3`（ARMv7 + ARM64），而两个 `transformpose` 拼写变体都启用 Android ARM64，且二进制哈希不同。

处理步骤：

1. 对每个 `.so` 确认 `DllImport` 名称、Java/JNI 加载名、AAR/Gradle consumer 与 PluginImporter 平台勾选。
2. 分别构建 ARMv7、ARM64 和（若产品仍支持）x86，比较 APK 的 `lib/<abi>/` 内容与运行日志。
3. 仅在证明某个拼写变体未加载、或 x86 明确不在发布矩阵后，删除对应 ABI 文件与 `.meta`。

**完成标准**：每个删除均有 ABI 构建和实际启动日志；不得以“名字像拼写错误”替代 native 加载验证。

**静态审计结果（2026-07-30）**：`libtransfrompose.so` 与 `libtransformpose.so` 均为不同 SHA-256 的 ARM64 ELF（均含 debug info、均在 PluginImporter 中启用 Android/ARM64）；源码、Gradle 和文本配置未发现二者的加载名。因此暂不能判定任一拼写变体冗余。`libs/x86/` 的 AVPro/Audio360/Opus 库也无法以当前 `ARMv7 + ARM64` 架构配置替代实际打包验证；待 Build Settings 场景确定后，构建包并检查 APK `lib/<abi>/` 与启动日志。
