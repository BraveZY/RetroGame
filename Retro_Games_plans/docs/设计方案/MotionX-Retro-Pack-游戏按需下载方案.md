# MotionX Retro Pack 游戏按需下载方案

> 本文用于明确 `MotionX Retro Pack / 复古体感包` 从主题馆进入游戏列表后，如何处理默认内置游戏、远程游戏下载、包体控制和内容更新。它补充产品定义、移动端原型和云端内容编排关系，不替代具体游戏玩法设计。

## 1. 设计目的

本方案用于明确 `MotionX Retro Pack / 复古体感包` 的游戏内容交付方式，在手机版 / 平板移动端优先的首发路径下，通过“默认内置基础内容 + 远程按需下载扩展内容”的结构，同时服务安装转化、促活留存、内容增收和长期运营更新。按需下载不是单纯的技术拆包方案，而是让首包更轻、首局更快、内容上新更灵活、活动和主题包更容易变现的产品机制。

重点在于让首包足够轻、首局足够快、后续内容足够灵活。默认内置基础游戏保证用户安装后能立刻体验核心闭环，降低首次流失；远程游戏、节日活动、主题皮肤和挑战内容则承担持续上新、促活留存和内容增收。云端清单负责控制展示、状态、优先级、灰度和下架，Addressables 负责资源依赖、缓存、版本和远程下载。远程包只放资源、场景、Prefab 和配置，不下发 C# 逻辑代码，避免为了运营更新牺牲审核、安全和调试边界。

## 2. 结论

本方案采用 **Unity Addressables Remote Content + 云端游戏清单**。

安装包默认带 10 个基础游戏，其它游戏在用户点击开始时按需下载。这样既能让首包具备足够完整的首发体验，也能避免后续扩展内容继续推高包体。

```text
首页
  -> 选择主题馆
    -> 游戏列表
      -> 默认内置游戏：直接开始
      -> 未下载游戏：点击开始后下载
      -> 已下载游戏：直接开始
```

## 3. 为什么不用全部内置

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 全部游戏随包发布 | 实现简单，离线可玩 | 包体快速膨胀，首发审核和下载转化压力大 |
| 自己写 AssetBundle 下载系统 | 完全可控 | 需要自建依赖、版本、缓存、校验和回滚逻辑，维护成本高 |
| Addressables 远程内容 | Unity 原生支持依赖、缓存、Catalog 和远程包 | 需要提前规划资源分组、CDN 和版本流程 |

当前阶段最合适的是第三种：**Addressables 承担资源下载，云端清单承担内容展示和运营控制。**

## 4. 内容分层

| 层级 | 是否进安装包 | 说明 |
| --- | --- | --- |
| App 框架 | 是 | 启动、导航、主题馆、游戏列表、设置、结算等基础流程 |
| 体感识别能力 | 是 | 摄像头权限、人体识别、动作输入、基础校准 |
| 公共资源 | 是 | 通用 UI、字体、基础音效、加载页、错误提示、公共材质 |
| 默认 10 个基础游戏 | 是 | 首发基础内容，安装后可立即体验 |
| 其它游戏资源 | 否 | 通过 Addressables Remote Group 按需下载 |
| 活动、皮肤、扩展资源 | 否 | 后续运营内容，默认远程化 |

## 5. 默认内置 10 个游戏

默认内置游戏覆盖首批主题馆，让用户安装后不需要额外下载就能看到一个完整的基础游戏列表。10 个内置游戏可以按主题馆分布，而不是平均分配。

| 主题馆 | 默认内置规划 | 目的 |
| --- | --- | --- |
| 童年操场 | 3-4 个 | 覆盖多人、反应、跑跳、童年操场氛围 |
| 客厅街机 | 3-4 个 | 覆盖短局、刷分、排行榜、反应挑战 |
| 电视健美操 | 2-3 个 | 覆盖家庭跟练、节奏、低冲击运动 |

这 10 个游戏不只是内容数量要求，它们负责保证基础包的体验厚度：

```text
选择主题 -> 选择游戏 -> 识别准备 -> 游戏中 -> 结算 -> 奖励反馈
```

默认 10 个游戏必须优先选择体积可控、复用公共资源多、玩法稳定的内容。重素材、活动型、节日型和实验玩法可以放到远程按需下载。

## 6. 游戏列表数据

游戏列表不写死在客户端里，而是由云端 `content_manifest.json` 控制。客户端启动后拉取并缓存一份，本地离线时使用上一次成功缓存的数据。

示例结构：

```json
{
  "catalog_version": "2026.06.18",
  "games": [
    {
      "game_id": "playground_freeze",
      "theme_id": "childhood_playground",
      "title": "操场木头人",
      "delivery": "bundled",
      "addressable_label": "game_playground_freeze",
      "size_mb": 0,
      "status": "available",
      "priority": "featured"
    },
    {
      "game_id": "arcade_boxing",
      "theme_id": "living_room_arcade",
      "title": "街机拳击",
      "delivery": "remote",
      "addressable_label": "game_arcade_boxing",
      "size_mb": 85,
      "status": "available",
      "priority": "normal"
    }
  ]
}
```

## 7. 游戏状态

客户端需要把游戏状态统一成可展示、可点击的状态机。

| 状态 | 含义 | UI 表现 | 点击行为 |
| --- | --- | --- | --- |
| `bundled` | 安装包已自带 | 开始 | 直接进入准备页 |
| `not_downloaded` | 远程游戏，尚未下载 | 下载并开始 / 开始 | 先下载依赖，再进入准备页 |
| `downloading` | 正在下载 | 进度条、暂停或取消 | 禁止重复开始 |
| `installed` | 已下载到本地缓存 | 开始 | 直接进入准备页 |
| `update_required` | 本地版本过旧 | 更新 | 更新完成后进入 |
| `unavailable` | 未上架或暂不可用 | 灰态 | 不允许进入 |

## 8. 点击开始流程

```text
用户点击开始
  -> 读取 game_id
  -> 检查云端清单状态
  -> 检查 Addressables 依赖是否已下载
    -> 已下载：加载游戏场景或 Prefab
    -> 未下载：显示下载确认和大小
      -> 下载完成：校验成功
        -> 加载游戏
      -> 下载失败：提示重试 / 稍后再试
```

首版可以把按钮文案做得简单：

| 场景 | 按钮 |
| --- | --- |
| 内置游戏 | 开始 |
| 未下载游戏 | 下载并开始 |
| 已下载游戏 | 开始 |
| 需要更新 | 更新后开始 |
| 网络不可用 | 稍后再试 |

## 10. 代码和资源边界

远程包只放：

- 场景
- Prefab
- 配置
- 图片
- 音频
- 动画
- 材质
- Timeline / VFX
- 关卡数据

新的 C# 逻辑代码不作为远程下载内容。核心原因：

| 原因 | 说明 |
| --- | --- |
| 移动端审核风险 | App Store / 部分安卓渠道对动态代码更新更敏感 |
| 调试和回滚复杂 | 代码和资源版本错配时很难定位 |
| 安全边界更差 | 动态逻辑更新容易引入不可控行为 |
| 体感输入需要稳定 | 动作识别、计分、结算等核心逻辑应随 App 版本验证 |

更稳的做法是：

```text
通用玩法代码随 App 发布
远程内容通过配置、Prefab、场景和资源组合出新游戏
```

如果后续确实需要扩展新玩法逻辑，应通过 App 版本更新发布，而不是远程热更代码。

## 11. CDN 和缓存

远程资源放在 CDN 或对象存储上。

| 能力 | 要求 |
| --- | --- |
| 下载 | 支持断点重试或失败重试 |
| 缓存 | Addressables 本地缓存，避免重复下载 |
| 版本 | Remote Catalog 控制资源版本 |
| 灰度 | 云端清单控制展示范围 |
| 下架 | 清单隐藏，不强删用户本地缓存 |
| 清理 | 设置缓存上限，低频内容可释放 |

## 12. 阶段策略

| 阶段 | 内容策略 | 下载策略 |
| --- | --- | --- |
| MVP | 先用少量样板验证完整流程 | 可先内置验证，不强依赖远程下载 |
| 首发基础包 | 10 个基础游戏 | 默认 10 个内置，其它按需下载 |
| 成长阶段 | 10 个内置 + 更多远程内容 | 主题馆内容池 + 展示优先级 + 活动内容远程化 |
| 运营阶段 | 每月活动、皮肤、挑战 | 云端清单控制上架、展示优先级、灰度和下架 |

## 13. 和主题馆的关系

主题馆负责组织内容，游戏下载方案负责交付内容。

```text
主题馆
  -> 只决定用户看到哪些游戏

云端清单
  -> 决定游戏是否显示、展示优先级和是否可下载

Addressables
  -> 决定游戏资源从本地加载还是远程下载
```

不要把主题馆做成资源包边界。一个主题馆里可以同时存在内置游戏和远程游戏。

例如：

| 主题馆 | 游戏 | 交付方式 |
| --- | --- | --- |
| 童年操场 | 操场木头人 | 内置 |
| 童年操场 | 跳房子 | 内置 |
| 童年操场 | 丢手绢 | 远程 |
| 客厅街机 | 投篮机 | 内置 |
| 客厅街机 | 拳击机 | 内置 |

## 14. 用户体验原则

| 原则 | 说明 |
| --- | --- |
| 不让用户先下载一堆内容 | 进入主题馆后先看到游戏，点击具体游戏时再下载 |
| 默认游戏必须立即可玩 | 首次安装不能只有空列表或大量下载提示 |
| 下载提示要说清楚大小 | 例如 `需要下载 85 MB` |
| 下载失败不能卡死流程 | 保留返回主题页、重试、稍后再试 |
| 已下载内容要像本地内容一样开始 | 不重复打扰用户 |
| 主推位优先放已内置或已下载内容 | 降低第一次体验阻力 |

## 15. 当前执行口径

当前版本按以下口径推进：

1. 安装包默认带 10 个基础游戏。
2. 游戏列表由云端 `content_manifest.json` 驱动。
3. 其它游戏使用 Unity Addressables Remote Group 按需下载。
4. 点击开始时才触发下载，不在进入主题馆时批量下载。
5. 远程包只放资源、场景、Prefab 和配置，不远程下发 C# 逻辑代码。
6. MVP 阶段先跑通状态机和下载闭环，首发基础包按 10 个内置游戏落地，再接 CDN、灰度、下架和缓存清理。

一句话结论：

> 用 Addressables 做可下载游戏内容，用云端 Manifest 做游戏列表和状态，不把所有游戏都塞进首包。
