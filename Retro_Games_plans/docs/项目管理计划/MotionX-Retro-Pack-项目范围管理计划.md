# MotionX Retro Pack / 复古体感包 项目范围管理计划

> 本文按照 PMP / PMBOK 范围管理思路编写，用于定义 `MotionX Retro Pack / 复古体感包` 项目的范围规划、范围定义、WBS、范围基准、验收标准、范围控制和变更机制。当前执行优先级以手机版本为主，先验证手机 / 平板产品包，再复用到大屏端、Lite、Game Pass 和 OEM 场景。产品定义见 [MotionX-Retro-Pack-产品定义.md](./MotionX-Retro-Pack-产品定义.md)，立项说明见 [MotionX-Retro-Pack-项目立项说明书.md](./MotionX-Retro-Pack-项目立项说明书.md)。`童年的一天` 与主题馆内容池的关系见 [童年的一天_云端内容编排关系.md](../设计方案/童年的一天_云端内容编排关系.md)。MVP 核心闭环、系统模块分层和双端产品架构见 [MotionX-Retro-Pack-MVP与系统模块分层方案.md](../设计方案/功能模块/MotionX-Retro-Pack-MVP与系统模块分层方案.md)。家长控制、内容限制和国内联网合规边界见 [MotionX-Retro-Pack-家长控制与内容限制管理设计方案.md](../设计方案/功能模块/MotionX-Retro-Pack-家长控制与内容限制管理设计方案.md)。

## 1. 文件目的

本计划用于明确项目“做什么、不做什么、做到什么程度算完成”，避免手机版 MVP 阶段因复古主题、运营活动、海外区域定制、大屏端适配和渠道诉求不断扩张，导致首批样板无法按时验证。

本计划重点覆盖：

1. 范围管理方法。
2. 项目范围说明。
3. 可交付成果。
4. 不包含范围。
5. 工作分解结构 WBS。
6. 范围基准。
7. 范围验收标准。
8. 范围变更控制。
9. 范围蔓延防控。

## 2. 范围管理目标

项目范围管理目标：

1. 保证 MVP 聚焦三个主题馆方向和三个样板内容：`童年操场 / 操场木头人`、`客厅街机 / 电玩城投篮机`、`电视健美操 / 家庭电视健美操`。
2. 保证首版以手机 / 平板为主，只验证主题入口、内容条目结构、基础包装流程、触控选择、摄像头权限、横屏取景、动作识别稳定性和家庭复玩意愿。
3. 明确 `童年的一天` 是云端编排层 / 播单层，不是第四个主题馆，也不在 MVP 阶段复制一套独立内容库。
4. 明确实时合影、换装、完整西游剧情、复杂运营系统和深度 OEM 定制不进入 MVP。
5. 让产品、技术、美术、运营、渠道对当前版本边界有统一口径。
6. 所有新增需求必须经过范围变更评估，不直接进入当前版本。

## 2.1 平台优先级

当前范围按以下平台顺序执行：

| 平台 | 当前定位 | 范围处理 |
| --- | --- | --- |
| 手机 / 平板 | 当前主版本，优先验证 MVP 和首发内容 | 竖屏浏览、触控选择、摄像头权限、横屏取景、移动端 HUD、结算保存 / 分享、移动端性能和发热验证 |
| 大屏电视 / 电视盒子 | 后续同源产品包，不作为当前 MVP 主交付 | 复用同一游戏 ID、规则、流程、奖励和内容池；UI、输入提示、分辨率和站位提示另行适配 |
| Lite / RK3566 / OEM | 渠道扩展和商业复制方向 | 当前只保留范围边界和复用口径，不抢占手机版 MVP 资源 |

平台红线：

1. 不把手机端做成电视遥控器或奖励册，手机端是独立随身复古体感产品。
2. 不为了大屏端提前修改手机版 MVP 的内容结构、节奏或验收标准。
3. 不形成移动端和大屏端两套游戏内容池、两套评分规则或两套活动规则。

## 3. 范围管理方法

本项目采用“阶段范围基准 + Gate 验收 + 变更控制”的方式管理范围。

管理流程：

1. **规划范围管理**：定义本文中的范围管理方法、验收规则和变更流程。
2. **收集需求**：从产品定义、立项说明、运营方案、风险登记册和渠道反馈中收集需求。
3. **定义范围**：明确 MVP、首发、成长阶段分别包含和不包含的内容。
4. **创建 WBS**：把项目拆成可交付成果和工作包。
5. **确认范围**：通过阶段 Gate 验收成果是否满足范围基准。
6. **控制范围**：所有新增、删除、替换和延期需求必须走变更流程。

## 5. 项目范围说明

### 5.1 项目总体范围

`MotionX Retro Pack / 复古体感包` 是现有体感内容的二次组织、主题包装和轻量样板验证项目，不是从零开发一批重游戏。当前版本主要面向手机 / 平板，先证明移动端随身体感体验成立，再把同源内容池复用到大屏端和渠道包。

项目总体范围包括：

1. 新增 `时光体感馆 / Time Play` 主题入口。
2. 设计复古主题馆结构。
3. 建立三个主题馆的内容池口径：`童年操场`、`客厅街机`、`电视健美操`。
4. 制作首批三个 MVP 样板内容。
5. 为游戏内容建立基础内容条目结构，包括内容 ID、主题馆、动作标签、人数、时长、强度、状态和可选时段标签。
6. 建立单个复古体感游戏的包装流程。
7. 制作手机近距离可读、竖屏浏览和横屏游戏可用的复古 UI。
8. 制作原创复古音乐 demo。
9. 建立带童年元素的结算界面，以及独立奖励卡片、称号和回忆标签。
10. 支持基础多人形式：轮流、分队或粗粒度同屏。
11. 建立 MVP 数据指标和埋点口径。
12. 建立国内联网发布所需的账号、实名、防沉迷、未成年人限制、隐私提示和合规拦截最小闭环。
13. 为后续 Game Pass、节日活动、云端编排路线、大屏端复用和 OEM 定制保留轻量扩展结构。

### 5.2 MVP 范围

MVP 只用于验证方向，不等同完整上线版本。

| 模块 | MVP 包含范围 |
| --- | --- |
| 主题入口 | `时光体感馆 / Time Play` 基础入口 |
| 主题馆 | 童年操场、客厅街机、电视健美操三个方向的最小呈现 |
| 样板游戏 | 操场木头人、电玩城投篮机、家庭电视健美操 |
| 内容条目 | 每个样板具备内容 ID、主题馆、动作标签、人数、时长、强度和状态 |
| 时段标签 | 可预埋 `清晨`、`课间操场`、`放学之后`、`回到家里` 等弱标签，但不做完整时间线主入口 |
| 包装流程 | 回忆开场、入戏式识别、核心玩法、轻松反馈、结算界面 |
| UI | 手机近距离可读的基础复古 UI，覆盖竖屏首页 / 主题页 / 结算 / 奖励，以及横屏识别 / 游戏 HUD |
| 端侧能力 | 触控选择、摄像头权限、横屏取景、设备摆放提示、保存 / 分享入口 |
| 音乐 | 一套原创复古音乐 demo 和基础音效 |
| 多人 | 轮流、分队或粗粒度同屏，不做精确同步率 |
| 数据 | 入口点击、游戏点击、首局完成、复玩、退出、识别失败 |
| 合规 | 国内联网发布时，完成账号、实名、防沉迷状态、未成年人限制、付费拦截、隐私提示和合规拦截原因码的最小闭环 |
| 测试 | iOS / Android 手机和平板的摄像头权限、取景、识别、性能和发热基础验证 |

### 5.3 首发范围

首发版本在 MVP 通过后扩展，目标是形成可销售的主题包。

| 模块 | 首发建议范围 |
| --- | --- |
| 内容数量 | 6-10 个复古主题内容 |
| 主题馆 | 稳定开放童年操场、客厅街机、电视健美操 |
| 内容池 | 内容按主题馆沉淀，支持按动作、强度、人数和时段标签筛选 |
| 弱编排 | 可出现弱时段标签或推荐顺序，但不把 `童年的一天` 做成必须完整通关的主线 |
| 活动 | 1-2 个轻量首发挑战 |
| 排行榜 | 优先支持街机类高分榜或本地榜 |
| 结算 | 分数、称号、回忆标签、带童年元素的结算界面 |
| 奖励 | 独立奖励卡片，可承接贴纸、徽章或收藏项 |
| 宣传素材 | 移动端商店主图、竖屏 / 横屏截图、15 秒短视频、渠道一页纸 |
| 数据复盘 | 支持按主题馆、样板、渠道拆分基础指标 |

### 5.4 成长期范围

成长阶段用于支撑订阅运营和国内主题扩展。

| 模块 | 成长期建议范围 |
| --- | --- |
| Game Pass | 每周家庭挑战、每月主题活动 |
| 节日活动 | 节日游园会、暑假运动会、春节游园等 |
| 国内主题皮肤 | 中国童年操场、春节游园、暑假运动会、西游童年神话等国内包装 |
| 时间线结构 | 内容达到 10-20 个后启用《童年的一天》编排入口 |
| 云端编排 | 支持 `playlist_id`、时段、内容 ID、展示文案、资源地址和运行参数下发 |
| 轻量收集 | 称号、徽章、纪念标签，不做 RPG 数值成长 |

### 5.5 游戏内容范围口径

游戏内容按“主题馆内容池 + 内容条目 + 编排路线”三层管理。

| 层级 | 范围定义 | 当前阶段处理方式 |
| --- | --- | --- |
| 主题馆内容池 | `童年操场`、`客厅街机`、`电视健美操`，负责承载具体游戏和课程 | MVP 必须成立，首发继续扩内容 |
| 内容条目 | 单个可运行游戏或课程，如 `操场木头人`、`电玩城投篮机`、`家庭电视健美操` | MVP 每个样板都要有内容 ID、主题、动作、人数、时长、强度、状态 |
| 编排路线 | `童年的一天` 这类体验路线，从主题馆内容中取内容并排序 | MVP 只预留标签和结构；内容达到 10-20 个后再作为入口激活 |

范围红线：

1. `童年的一天` 不新增一套独立游戏目录。
2. `童年的一天` 不替代三个主题馆直接入口。
3. 客户端不写死固定内容顺序，只识别云端下发的路线和内容 ID。
4. MVP 3 个样板时只做主题馆入口和弱时段标签，避免时间线显空；首发扩展到 6-10 个内容后，可增加弱推荐顺序或轻量挑战，但仍不做强制通关时间线。

## 6. 不包含范围

以下内容不进入 MVP。

| 不包含项 | 原因 |
| --- | --- |
| 实时合影 / 换装 | 独立图像合成管线，成本高 |
| 完整西游剧情大冒险 | 过重，偏离短局主题包定位 |
| 精确家庭同步率 | 2D 多人遮挡和站位影响稳定性 |
| 真实地面落点判定 | 单目 2D 无深度，不稳定 |
| 前后纵深移动判定 | 超出稳定动作边界 |
| 真实老歌、影视音乐、明星或真实 IP | 版权和合规风险 |
| 把 `童年的一天` 做成第四个主题馆 | 会造成内容目录重复和产品层级混乱 |
| 客户端写死固定时间线内容顺序 | 后续云端运营、替换和个性化推荐会受限 |
| 复杂等级、装备、货币、体力系统 | 破坏轻量家庭短局体验 |
| 深度 OEM 底层玩法定制 | 会造成版本分叉和维护成本 |
| 大规模社交系统 | 不属于 MVP 验证目标 |
| 大量吐槽文案分支 | 本地化和维护成本高 |
| 大屏端完整 UI、遥控器适配和电视盒子渠道包 | 当前主版本是手机 / 平板，后续在同源内容池稳定后再做 |

## 8. 范围基准

范围基准由以下三部分组成：

1. **项目范围说明**：本文第 5 节和第 6 节。
2. **WBS**：本文第 7 节。
3. **WBS 词典**：本文第 9 节。

任何新增、删除、替换或延期工作，只要影响范围基准，都必须走范围变更流程。

## 9. WBS 词典

| WBS 编号 | 工作包 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| 2.1 | 主题入口定义 | `时光体感馆 / Time Play` 入口方案 | 用户能理解这是复古家庭体感入口 |
| 2.2 | 主题馆内容池结构 | 三个主题馆与内容归属说明 | `童年操场`、`客厅街机`、`电视健美操` 不与 `童年的一天` 混层 |
| 2.3 | 三个 MVP 样板内容设计 | 三个样板玩法说明 | 每个样板目标、动作原语、节奏、结算明确 |

| 2.5 | 单局体验流程 | 开场、识别、玩法、反馈、结算流程 | 用户 30 秒内理解玩法 |
| 2.6 | 移动端页面流程 | 竖屏首页、主题页、玩法确认、权限 / 横屏取景、游戏中、结算、奖励卡片 | 手机端不是电视遥控器，能独立完成完整游戏闭环 |

| 4.1 | 移动端复古 UI 视觉规范 | 基础 UI 规范 | 竖屏浏览清晰，横屏 HUD 不遮挡摄像头主体，关键按钮适合触控 |

## 10. 范围验收标准

### 10.1 MVP 验收标准

MVP 通过必须满足：

1. 三个样板都有完整闭环：开场、识别、玩法、反馈、结算。
2. 三个样板都能归属到明确主题馆，并具备内容 ID、动作标签、人数、时长、强度和状态。
3. 用户 5 秒内知道要做什么动作。
4. 用户 30 秒内理解玩法。
5. 单局时长控制在 1-3 分钟。
6. 手机 / 平板上没有明显权限、取景、识别、发热和性能阻断。
7. 结算页能展示分数、称号和回忆标签。
8. 数据埋点能支持按主题馆和内容维度做基础复盘。
9. 素材和音乐通过版权检查。
10. `童年的一天` 只作为后续编排结构预留，不作为 MVP 第四主题馆验收。
11. 手机端能独立完成首页、主题页、玩法确认、权限 / 横屏取景、游戏中、结算和奖励卡片闭环。
12. 国内联网版本能正确处理未登录、未实名、未成年人非可玩时段、时长超限、付费受限和隐私提示缺失等拦截状态。

### 10.2 首发验收标准

首发版本通过必须满足：

1. 至少 6 个内容可稳定进入和完成。
2. 三个首批主题馆可稳定浏览。
3. 内容池支持按主题馆、动作、强度、人数和时段标签做基础筛选或推荐。
4. 首发活动不会影响主游戏入口。
5. 移动端商店主图、截图、视频与真实体验一致。
6. 基础排行榜或本地高分榜可用。
7. 渠道话术不超过产品能力边界。

### 10.3 成长期验收标准

成长阶段扩展必须满足：

1. 首批主题馆已有稳定点击和复玩数据。
2. 至少一个家庭挑战活动表现良好。
3. 新内容不是简单换皮凑数。
4. 国内主题皮肤有明确用户记忆和渠道依据。
5. 《童年的一天》结构只在内容达到 10-20 个后启用。
6. 云端编排路线可通过 `playlist_id` 下发，客户端不写死固定内容顺序。

## 11. 范围确认流程

范围确认由项目负责人组织，按阶段 Gate 进行。

```text
工作包完成
→ 负责人自检
→ 产品 / 技术 / 运营 / QA 验收
→ 对照范围基准确认是否完成
→ 记录验收结论
→ 未通过项进入修复或变更流程
```

验收结论：

| 结论 | 含义 |
| --- | --- |
| 通过 | 满足当前阶段范围基准 |
| 有条件通过 | 存在非阻断问题，允许进入下一阶段但需记录 |
| 未通过 | 影响范围目标，必须修复、降级或变更 |
| 转后续版本 | 当前阶段不处理，进入后续版本池 |

## 12. 范围变更控制

以下情况必须提交范围变更：

1. 新增样板游戏。
2. 新增主题馆。
3. 把 `童年的一天` 从编排路线升级为独立主题馆或独立内容包。
4. 将云端编排路线改为客户端写死的固定内容顺序。
5. 新增实时合影、换装、剧情、养成或社交系统。
6. 新增真实地面落点、前后纵深、精确同步率玩法。
7. 新增 OEM 深度定制。
8. 新增需要大量美术、音乐或动画生产的内容。
9. 推广或渠道承诺新增当前版本没有的能力。
10. 将大屏端完整 UI、遥控器适配、电视盒子渠道包提前并入手机版 MVP。
11. 弱化或移除国内联网版本中的账号实名、防沉迷、未成年人限制、隐私提示或付费拦截。

变更流程：

```text
提出变更
→ 描述变更内容和业务理由
→ 评估对范围、进度、成本、质量、风险的影响
→ 判断是否进入当前版本
→ 项目负责人组织决策
→ 更新范围基准、风险登记册和相关文档
```

变更决策：

| 决策 | 使用场景 |
| --- | --- |
| 接受 | 变更必要且不破坏当前阶段目标 |
| 延期 | 有价值但不进入当前版本 |
| 降级 | 保留目标，但缩小实现范围 |
| 拒绝 | 与项目定位、技术边界或版权边界冲突 |
| 升级 | 涉及重大商业、法务或资源决策 |

## 13. 范围蔓延防控

重点防控以下范围蔓延：

| 蔓延类型 | 表现 | 控制方式 |
| --- | --- | --- |
| 内容蔓延 | 想把更多现有游戏都塞进首版 | MVP 固定三个样板，首发再扩 6-10 个 |
| 编排蔓延 | 内容不足时就把 `童年的一天` 做成完整主线 | 首发只做主题馆入口和弱时段标签，10-20 个内容后再激活编排入口 |
| 层级蔓延 | 把 `童年的一天` 当成第四个主题馆 | 坚持主题馆产内容、`童年的一天` 做路线编排 |
| 技术蔓延 | 想做精确同步、真实落点、纵深移动 | 坚守 2D 单目动作边界 |
| 平台蔓延 | 手机版 MVP 未稳定前就做完整大屏端、电视盒子或 OEM 包 | 当前先完成手机 / 平板闭环，大屏端只保留同源复用口径 |
| 合规蔓延 | 把账号、实名、防沉迷、隐私提示和未成年人限制当成上线后再补的运营插件 | 国内联网版本把合规拦截作为 P0 门槛，MVP 就验证原因码和提示链路 |
| 运营蔓延 | 想做等级、装备、货币、复杂任务 | 只做称号、徽章、挑战、结算标签 |
| 渠道蔓延 | OEM 要求改底层玩法 | 定制限制在皮肤、音乐、排序、活动图和话术 |
| 美术蔓延 | 首版想做大量海外区域皮肤和复杂动画 | MVP 只做国内关键包装、结算界面和静态奖励卡片 |
| 叙事蔓延 | 西游方向变成完整剧情冒险 | 西游只作为后续节假日主题，不进 MVP |

## 15. 一句话总结

`MotionX Retro Pack / 复古体感包` 的范围管理核心是：当前先做手机版 MVP，只证明三个主题馆方向、三个样板内容、移动端独立产品闭环和一套复古体感包装流程是否成立；首发再扩主题馆内容池和轻量活动；成长阶段再用云端编排把内容串成《童年的一天》；大屏端、Lite 和 OEM 在同源内容池稳定后再复用扩展。`童年的一天` 是路线，不是第四个主题馆。海外市场、海外皮肤和海外营销话术暂不进入当前范围，任何新增需求都必须先证明它服务当前阶段目标，否则进入后续版本池。
